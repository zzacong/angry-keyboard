# Draw each hit from a weighted sound pool, and count voices per pool

The four arrow keys should play one of four impact sounds at random, and the default keys should mostly keep the shotgun but sometimes play a reaction. Both need a binding whose sound is not known until it plays, which the model did not have: a binding pointed at exactly one sound, and the resolver is a pure function of the keystroke and the pack.

So a binding points at a sound pool, and the sound is drawn in the audio output, not the resolver. The resolver still returns a binding from a keystroke alone, so it stays pure and its tests stay plain values with no generator. A pool carries a weight per sound and draws in proportion to it; equal weights are the uniform case, which leaves the arrow pool's draws unchanged. Weights live on the pool because the pool is already the shared unit: bindings that share a pool share its draw and its voice count.

`AudioOutput.play` counts voices against the pool rather than the sound, using the triggering binding's voice count as the cap. Bindings that share a pool must therefore use the same count, and the shipped pack does. All four arrow bindings share one pool at a count of three, so retrigger keeps a single arrow voice and overlap caps the arrows at three together, no matter which sound each press drew. The catch-all is now an ordinary binding to a pool instead of a bare sound, which removes a special case from `SoundPack`.

A non-positive weight is rejected, matching the empty-pool precondition: a sound that never plays does not belong in the pool. Pool identity includes the weights, which is what voice counting wants. A reweighted pool is a different pool.

Considered and rejected: drawing in the resolver with an injected generator. It keeps the choice in one place, but it makes the resolver impure and every resolver test has to carry a seeded generator to stay deterministic. Considered and rejected: counting voices per sound. It is simpler in the engine, since a voice already knows its sound, but it lets fast arrow presses stack four independent pools, so retrigger would no longer mean one arrow voice at a time, which defeats the mode. Considered and rejected: repeating a sound in the list to weight it. It needs no new type, but the same sound appears many times, the weights are invisible in the data, and the pool stops being a set. Considered and rejected: a separate weighted pool type. It protects the uniform pool, but the audio engine and voice keying would handle two pool types for no gain.

The cost is that the audio engine now knows the pool as a voice key, and which sound plays is decided by a side-effecting component. That is where randomness already lives, next to the per-hit pitch and gain spread, so the resolver and the model stay deterministic.
