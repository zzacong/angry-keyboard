# Add in-app updates with Sparkle 2

AngryKeyboard ships from GitHub Releases and has never had an updater, so a release only reaches someone who notices it and reinstalls by hand. We add [Sparkle 2](https://sparkle-project.org) as the repo's first third-party dependency: the production app checks a feed once a day, offers the update from its status menu, and installs it on a click.

The setup stays inside ADR 0007. Sparkle needs no Developer ID and no notarization. It trusts an EdDSA signature on the release archive, checked against a public key the app carries. The update is signed with the same self-signed certificate, so the Input Monitoring grant survives, and Sparkle strips the quarantine flag from what it downloads, so Gatekeeper still only interrupts the first, manual install. The feed is one more asset on the release, at `releases/latest/download/appcast.xml`, and the app compares `CFBundleVersion`, the Actions run number from ADR 0008.

Dev builds never check, gated by the `AK_ENABLE_UPDATES` build setting, because a dev build has no release to update to and updating one would fight the side-by-side setup in ADR 0009. Both channels share one Xcode target, so Sparkle is linked and embedded in Dev too; it is simply never constructed there, and the dev channel behaves exactly as before. The check is automatic but the install needs a click, so there is no silent background install, no phased rollout, and no critical-update flag. Binary deltas are skipped because the app is small and GitHub serves it quickly.

Considered and rejected: a check-only feature that opens the release page. It needs no dependency, but it makes every update a manual reinstall, which is the problem being solved. Considered and rejected: a hand-rolled downloader and installer. It avoids a dependency but reinvents Sparkle's signing, atomic swap, and quarantine handling. Considered and rejected: hosting the feed on the marketing site. It decouples the feed from asset-upload timing, but couples app releases to site deploys, and the `releases/latest` window it avoids is the same one the site's download button already lives with. Considered and rejected: a separate dev feed, because dev has no releases to update to.

Consequence: the EdDSA private key joins the signing certificate as a release-critical secret. If the EdDSA key is lost, existing installs are stranded: they carry the old public key, and Sparkle's fallback expects a Developer ID signature this self-signed app does not have, so users reinstall by hand. If the signing certificate is lost, updates still work but every recipient grants Input Monitoring again.
